# Модуль Management (Панель Керівництва)

## 1. Загальний опис модуля
Модуль призначений для верхньоуровневого контролю виробничих процесів веб-студії. Він дозволяє Адміністратору (Керівництву) ставити глобальні завдання для Project Manager-ів (PM), контролювати стадії виконання проєктів клієнтів та відстежувати дедлайни без занурення у мікроменеджмент лінійних спеціалістів.

## 3. Бізнес-логіка та життєвий цикл глобальних завдань

Процес контролю будується навколо сутності `global_tasks`. Керівництво формує пул макро-завдань, прив'язаних до конкретного проєкту та конкретного PM-а (наприклад: *"Провести брифінг компанії X та підписати договір"* або *"Передати дизайн-макет проєкту Y на етап верстки"*).

### Стадії виконання завдання (Task Statuses):
1.  `pending` (Очікує виконання) — Завдання створене Адміністратором, але PM ще не взяв його в активну роботу.
2.  `in_progress` (У роботі) — PM взяв завдання на виконання, воно знаходиться в поточному фокусі.
3.  `review` (На перевірці) — PM виконав макро-крок і передав завдання на перевірку Керівництву. Поле `result_url` є повністю опціональним (nullable) артефактом здачі.
4.  `completed` (Завершено) — Адміністратор підтвердив виконання завдання через `/approve`. Етап вважається офіційно закритим.
5.  `overdue` (Протерміновано) — Системний стан, який автоматично підсвічується в інтерфейсі, якщо поточна дата перевищує встановлений `deadline_at`, а завдання все ще не перейшло в статус `completed`.

### Функціонал формування та призначення завдань Керівництвом
Глобальні завдання для PM-ів створюються Адміністратором вручну в інтерфейсі панелі управління. 
*   **Обов'язкові зв'язки (FK):** При створенні завдання бекенд вимагає `project_id` та `pm_id` (відповідальний менеджер, у сідері зафіксовано `id: 2`).
*   **Автоматизація при створенні:** Коли Адміністратор створює задачу, бекенд автоматично переводить статус проєкту (`projects.status`) у стан `briefing`.

## 4. Специфікація API-ендпоінтів модуля

Усі запити приймають та повертають дані виключно у форматі `application/json` із Bearer-авторизацією Sanctum.

### Ендпоінти для Адміністратора (Керівництва) — `middleware(['role:admin'])`
*   `POST /api/v1/management/tasks` — Створення нового глобального завдання для конкретного PM-а з автотрансляцією статусу проєкту.
*   `GET /api/v1/management/tasks/list` — Перегляд усіх глобальних завдань у системі з гнучкою фільтрацією за менеджером (`?pm_id=X`), проєктом, статусом та прапорцем протермінування (`?is_overdue=1`).
*   `PUT /api/v1/management/tasks/{id}/update` — Повне редагування тексту, дедлайну, `result_url` або перепризначення задачі на іншого PM-а.
*   `PATCH /api/v1/management/tasks/{id}/approve` — Підтвердження виконання завдання Керівництвом. Переводить завдання в статус `completed`.
*   `DELETE /api/v1/management/tasks/{id}` — Видалення завдання (дозволено строго якщо воно перебуває в статусі `pending` або `in_progress`).
*   `GET /api/v1/management/dashboard/metrics` — Зведена аналітика для Адміністратора (кількість активних проєктів, відсоток успішно закритих завдань у строк (KPI), список усіх критично протермінованих дедлайнів по всій студії).

### Ендпоінти для Project Manager (PM) — `middleware(['role:admin,pm'])`
*   `GET /api/v1/pm/tasks` — Список глобальних завдань, призначених строго на поточного авторизованого PM-а на основі його токена (`where('pm_id', auth()->id())`).
*   `PATCH /api/v1/pm/tasks/{id}/status` — Зміна статусу завдання менеджером (переведення в `in_progress` або відправка на перевірку Керівництву в статус `review` з опціональним прикріпленням посилання у `result_url`).
