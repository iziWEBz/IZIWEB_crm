# Технічна архітектура бекенду CRM-середовища (PHP/Laravel)

**Головний інженерний принцип:** Створення системи за принципом **Headless (чистий REST API бекенд)**. Бекенд не відповідає за візуальний інтерфейс, а лише обробляє дані, валідує бізнес-логіку та керує доступами. Це дозволяє тестувати систему через **Postman** на першому етапі та підключати будь-які фронтенд-додатки у майбутньому без зміни логіки коду.

---

## 1. Архітектурний паттерн: Модульний моноліт (DDD-lite)

Щоб забезпечити головний критерій — **багатомодульність та поетапне додавання функціоналу**, ми відмовляємося від класичної структури Laravel (де всі контролери в одній папці, а моделі в іншій). Код проекту розділяється на **незалежні доменні модулі (Domain Modules)**.

Кожен модуль ізольований і містить власну логіку, маршрути (routes) та сервіси:
*   `app/Modules/IAM/` — Модуль автентифікації, реєстрації (строго логін/пароль), керування ролями та пермішенами.
*   `app/Modules/Management/` — Модуль для Керівництва (постановка глобальних завдань для PM-ів, контроль статусів).
*   `app/Modules/Onboarding/` — База знань, логіка послідовних кроків навчання, інтерактивні тести, чек-листи та трекінг відсіву (під 4 спеціалізації: дизайн, фронтенд, бекенд, SEO).
*   `app/Modules/ClientEnvironment/` — Інтерактивний бриф, конструктор документів, валідатор асистента, внутрішня тікет-система та прогрес-бар проекту.

*Взаємодія між модулями відбувається виключно через строго описані інтерфейси (Contracts/Services). Це дозволить у майбутньому безболісно винести будь-який модуль (наприклад, навчання) в окремий мікросервіс, якщо виникне така потреба.*

---

## 2. База даних: PostgreSQL

Для збереження даних обирається СУБД **PostgreSQL** з наступних причин:
1.  **Гнучкість Брифу (Тип даних `JSONB`):** Клієнтський бриф міститиме багато динамічних полів (масиви посилань на конкурентів, чек-бокси, кастомні текстові блоки). Нативна робота Postgres із `JSONB` дозволить зберігати схему брифу гнучко, але при цьому робити по ній швидку валідацію та вибірку на рівні бази даних.
2.  **Безпека Логів (Підписання договорів):** Postgres дозволяє створювати максимально ізольовані та захищені таблиці аудиту для логування цифрової згоди (фіксація IP, часу та данних браузера).

---

## 3. Технологічний стек та екосистема Laravel

Для швидкої розробки та забезпечення безпеки використовуються інструменти екосистеми PHP/Laravel:

*   **Автентифікація:** **Laravel Sanctum**. Забезпечує легку та безпечну роботу з токенами (Stateful/Token-based API). Ідеально підходить для тестування запитів через Postman. Жодних посилань на email — авторизація через `POST /api/v1/auth/login`.
*   **Керування доступами (RBAC):** **Spatie Laravel-Permission**. Дозволяє реалізувати гнучку матрицю прав, де Керівництво зможе вручну призначати ролі та контролювати пермішени (наприклад, `onboarding.read` для стажера, чи `contracts.sign` для клієнта).
*   **Генерація документів:** **barryvdh/laravel-dompdf** (або аналог). Дозволяє бекенду «на льоту» збирати HTML-шаблон договору, підставляти туди дані з профілю клієнта/брифу та генерувати фінальний захищений PDF-файл для ознайомлення в кабінеті.
*   **Автодокументація для Postman:** **Laravel Scribe** або **L5-Swagger**. Автоматично генерує колекцію ендпоінтів та документацію прямо з коду (із Doc-блоків контролерів). Розробники пишу закритий API — Postman-колекція оновлюється автоматично.

## 4. План розгортання першої версії бекенду (MVP)

1.  **Спринт 1: Фундамент та IAM.** Встановлення Laravel, налаштування PostgreSQL, інтеграція Sanctum та Spatie Permissions. Тестування в Postman створення користувачів та ручного призначення ролей Адміністратором.
2.  **Спринт 2: Контур «Навчання».** Створення таблиць курсів, кроків та трекінгу кандидатів. Наповнення бази знань тестовими даними (Seeders) для 4 технічних спеціалізацій. Тестування логіки блокування кроків.
3.  **Спринт 3: Контур «Клієнтське середовище».** Створення ендпоінтів для порційного збереження брифу та логіки валідації. Реалізація ендпоінту `POST /contracts/{id}/sign` для фіксації цифрового підпису та генерації незмінного логу безпеки.
